# LAZY vs EAGER Fetching, and the `LazyInitializationException`

## Overview
Every JPA association has a fetch strategy — when the related data actually gets loaded from the database. Getting this wrong is one of the most common sources of both performance bugs (N+1) and runtime crashes (`LazyInitializationException`) in Spring Boot applications.

---

## 1. The Two Strategies
- **`FetchType.EAGER`** — load the association immediately, as part of the same query that loads the owning entity (or via an immediate follow-up query).
- **`FetchType.LAZY`** — load the association only later, the first time code actually calls a getter on it. Hibernate returns a **proxy** in the meantime.

## 2. The JPA Spec's Default Trap
The default fetch type is **not** the same for every association type:

| Annotation | Default |
|---|---|
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |

`@ManyToOne` and `@OneToOne` default to EAGER — the opposite of what most people assume, and the opposite of what you almost always want. This project makes the fix explicit and calls it out in the code:

```java
// Task.java
/**
 * LAZY on purpose. @ManyToOne defaults to EAGER in JPA, which is a classic
 * gotcha worth naming out loud in an interview.
 */
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "project_id")
private Project project;
```

Left at the default, every single `Task` load would trigger an immediate join or extra query to fetch its `Project`, whether or not any caller ever needed it — silent, compounding overhead you didn't ask for.

---

## 3. How LAZY Actually Works: Proxies
With `fetch = LAZY`, `task.getProject()` inside an open session does **not** return `null` or the real entity — it returns a Hibernate-generated bytecode proxy (a runtime subclass of `Project`) with only the ID populated. The moment you call any other getter on it (`getName()`), the proxy fires a `SELECT` to fill itself in — this is called **lazy initialization**.

```java
Task task = taskRepository.findById(1L).orElseThrow();
Project p = task.getProject();      // no query yet - p is a proxy
String name = p.getName();          // triggers SELECT * FROM project WHERE id = ?
```

## 4. `LazyInitializationException`
This only works while the persistence context (Hibernate `Session`) that loaded the proxy is still open. If the transaction has already committed and the session closed — which is exactly the situation once a `@Transactional` service method has returned and control passes to the web layer — touching that proxy's uninitialized fields throws:

```
org.hibernate.LazyInitializationException: could not initialize proxy - no Session
```

This is precisely why `TaskResponse.from(task)` is called **inside** `TaskService.findById`, while the transaction (and therefore the session) is still open:

```java
// TaskResponse.java
/**
 * NOTE: touching task.getProject().getName() requires an open persistence
 * context or a fetch join - this is exactly where LazyInitializationException
 * bites people. We map inside a @Transactional service method.
 */
public static TaskResponse from(Task task) {
    return new TaskResponse(task.getId(), task.getTitle(), task.getDescription(),
            task.getStatus(), task.getDueDate(),
            task.getProject() != null ? task.getProject().getName() : null);
}
```
If this mapping happened later — say, in the controller, after the service method (and its transaction) had already returned — `task.getProject().getName()` would throw, because the session is gone by then.

## 5. Fixing It Without Going Back to EAGER
Switching back to `EAGER` "fixes" the exception but reintroduces the N+1 problem for every query that touches the association, whether needed or not — trading a crash for silent, compounding overhead. The correct fixes keep the association LAZY by default and load it eagerly **only for the specific query that needs it**:
- A JPQL **fetch join** (`join fetch t.project`), as `TaskRepository.findByStatusWithProject` does.
- `@EntityGraph`, as `ProjectRepository.findAll` does.
- Doing the mapping while the session is still open (this project's default approach for the simple cases).

---

## Interview Answer, Compressed
> "`@ManyToOne` and `@OneToOne` default to EAGER in the JPA spec, which surprises most people — `@OneToMany`/`@ManyToMany` default to LAZY. LAZY returns a proxy that lazily fires a query the first time you touch a getter on it, which only works while the owning session is still open. Touch it after the transaction has closed and you get `LazyInitializationException`. I set `@ManyToOne` explicitly to LAZY and either map to a DTO inside the transactional method, or use a fetch join / `@EntityGraph` for the specific queries that actually need the association — never flipping back to EAGER, since that just reintroduces N+1 everywhere."
